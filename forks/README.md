# Fork 维护

这里维护 [Yu15693/t3code-fork](https://github.com/Yu15693/t3code-fork) 的自用约定：在官方稳定版上叠加少量补丁，自行构建本机 macOS 桌面版，并手动选择升级时机。当前不使用 T3 Connect。开发环境和工程规则沿用 [AGENTS.md](../AGENTS.md)；处理具体补丁时，再阅读[补丁索引](#补丁索引)中对应的 Spec。

本页只记录长期约定，不记录当前版本。当前维护的补丁分支是版本最高的 `patches/v*`，日常使用的构建是最新的 `yu/v*` 标签，标签说明中记录该构建的验证结果：

```bash
git branch -a --list '*patches/v*'
git tag --list 'yu/v*' --sort=-version:refname -n20
```

本仓库公开。本页、Spec 和提交说明只写通用约定，不提及本机的私有仓库、个人 Agent 配置及其中的具体名称。

## 仓库与命名

| 对象                    | 用途                                                                 |
| ----------------------- | -------------------------------------------------------------------- |
| `upstream`              | 官方仓库：`https://github.com/pingdotgg/t3code.git`                  |
| `origin`                | 自己的 Fork：`https://github.com/Yu15693/t3code-fork.git`            |
| `main`                  | 仅从 `upstream/main` 快进同步，作为干净的上游参考                    |
| `patches/v<上游版本>`   | 以该官方稳定 tag 为起点的补丁栈，例如 `patches/v0.1.9`               |
| `yu/v<上游版本>-<序号>` | 带说明的标签，固定实际构建并安装的提交；序号区分同一基线下的多次构建 |
| `backup/…`              | 整理分支前的本地备份，不推送                                         |

上游 tag 按需获取，例如 `git fetch --no-tags upstream tag v0.1.9`，保持原名和指向。不使用 `git push --tags` 批量推送，自用标签单独推送；已推送的标签不移动。启用 Fork 的 Actions 前检查继承的 [release workflow](../.github/workflows/release.yml)，其中的定时任务和 `v*.*.*` 触发器需要单独适配。

## 补丁栈

每条补丁分支从官方 tag 开始，之后只有自用提交，`git log v<上游版本>..patches/v<上游版本>` 即为全部自用改动：

1. 第一个提交是维护配置：本页、[AGENTS.md](../AGENTS.md) 中的读取入口和 `mise.toml`。
2. 之后每个提交承接一个具体行为，连同它的 Spec、补丁索引条目、必要测试和提示词预算快照一起提交。

提交说明使用 Conventional Commits，记录实际行为、依赖和验证。从旧补丁分支迁移来的提交保留来源（`cherry-pick -x` 生成的记录，或手动整理时的 `Reorganized-from:`），适配新基线时有取舍的，简述冲突和处理方式；全新补丁没有来源记录。

日常维护只追加提交，补丁分支不改写历史，也不需要强推：

- 新的行为：新增一个独立提交。
- 修改已有补丁：用 `git commit --fixup=<原补丁提交>` 追加提交，标题自动成为 `fixup! <原提交标题>`。下次升级时再合入原提交，见[升级](#升级)。
- 新增补丁前，先核对已有配置和上游 issue/PR 是否已经提供相同能力。

## Spec

Spec 放在 `specs/YYYY-MM-DD-简洁中文主题.md`，日期为首次创建日期。每份记录一个行为补丁的背景、目标、方案、取舍和移除条件，随该补丁一起迁移。目标或方案发生实质变化时更新原文件；变化大到相当于新补丁时新建 Spec，并在旧文件中关联。

Spec 不记录某次构建的验证状态。源码检查写进提交说明，安装包验证写进对应 `yu/v*` 标签的说明。运行日志和二进制留在本地或发布产物中。

## 升级

每隔几周查看官方稳定版的发布说明，按需要决定是否升级；重要安全修复可以提前处理。补丁分支不跟随 `main` 或 Nightly。下文 `<旧>`、`<新>` 替换为实际的上游版本，例如 `v0.1.9`。

1. **准备**：确认工作区和暂存区干净，获取新 tag。需要更新参考分支时，仅快进合并 `upstream/main`；快进失败先核对差异，不强制重置。
2. **筛选补丁**：对 `<旧>..patches/<旧>` 中的每个行为补丁，查看新 tag 的实际代码和相关 issue/PR，判断上游是否已提供相同行为。已覆盖的补丁不再迁移，在新分支第一个提交的说明中写明 `Dropped: <原提交> <依据>`。除了功能和代码变化，也检查新版本给 Agent 的提示词、工具和参数是否与本机的 Agent 配置冲突；有冲突时调整本机配置，或新增补丁。
3. **迁移**：从新 tag 创建分支，按原顺序迁移提交，再把 `fixup!` 提交合入各自的原提交：

   ```bash
   git switch -c patches/<新> <新>
   git cherry-pick -x <要迁移的提交…>
   git rebase -i --autosquash <新>
   ```

   第二条命令可以直接传入范围 `<旧>..patches/<旧>`；有补丁不再迁移时，改为逐个列出要迁移的提交。遇到冲突时在当前补丁内解决，完成该提交前在提交说明中补充适配说明，不另建“解决冲突”提交。`rebase -i --autosquash` 会把每个 `fixup!` 排到对应原提交之后并标记合并，保存后历史中每个行为只剩一个提交。

4. **维护配置**：核对 `mise.toml` 与新版 [package.json](../package.json) 中的 Node、pnpm 版本及 `vite-plus` catalog 版本一致；本页和 Spec 中引用的文件和章节仍然存在。
5. **审查与验证**：用 `git range-diff <旧>..patches/<旧> <新>..patches/<新>` 核对每个补丁的保留、移除和适配，再按[构建与验证](#构建与验证)执行源码检查。
6. **发布分支**：验证通过后推送新的补丁分支。旧补丁分支保持不变，供追溯和回退；安装新版本按下一节单独进行。

升级验证未通过时，保留新分支现场继续修复，继续使用旧版本。

## 构建与验证

- **环境**：工具链由 `mise.toml` 固定，依赖按[开发指南](../docs/operations/development.md#first-checkout)准备，版本以 [package.json](../package.json) 和锁文件为准。
- **源码检查**：功能改动按 [AGENTS.md 的验证要求](../AGENTS.md#verifying)执行，推送前运行 `vp run check:changed <新>`，即以当前分支的上游 tag 为基准。修改运行时提示词时，还需按 [evals 指南](../evals/README.md)验证模型行为。只改文档时只检查入口、链接和命令来源。
- **构建**：macOS 打包入口为 `vp run dist:desktop:dmg`。系统依赖、默认不做发行签名的行为及产物位置见 [Desktop artifacts](../docs/operations/development.md#desktop-artifacts)。
- **安装包验证**：实际启动安装包，确认后台服务来自该安装包，并检查各 Spec 的目标行为；开发进程通过不能代替安装包验证。首次验证使用独立目录和测试数据，真实数据副本按 [Test data](../AGENTS.md#test-data) 准备。`T3CODE_HOME` 只控制服务状态，不能隔离 [Electron 资料目录](../apps/desktop/src/app/DesktopUserData.ts)；并行试用时还需核对应用身份和实际连接的服务。
- **打标签**：准备安装的构建通过验证后，在其提交上创建 `yu/v<上游版本>-<序号>` 带说明的标签，说明中记录应用版本、构建环境与命令、产物校验值和验证结果，然后单独推送该标签。

## 安装与回退

- **替换日常版本前**：确认活动任务可以中断，停止相关应用与服务，备份完整的 T3 home 和实际 Electron 资料目录，保留旧安装包。凭据和会话备份仅保存在本地；运行中只复制 SQLite 主文件不能充当完整备份。
- **回退**：数据迁移未必可逆。恢复时使用与旧标签对应的安装包和升级前的备份，备份之后产生的新记录会丢失。
- **切回官方版**：上游已满足全部需要时，用数据副本验证兼容后切回官方应用和服务，详见 [Updating T3 Code](../docs/user/updating.md)。
