# 子代理复用

## 背景与决定

上游 #24560 让发往已完成子线程的 `t3_thread_send` 作为新任务运行，结果会回报给父线程。同时，提示词改为只有独立审查轮次才新开 `delegate_task`，需要沿用同一子线程对话的后续工作用 `t3_thread_send`。第二天，#24850 精简提示词时把这条改成「Every new delegate review or re-check is a new `delegate_task`… never a `t3_thread_send`」：适用范围从独立审查扩大到所有审查和复核，延续子线程的写法也被删掉。v0.1.10 和上游 main 仍是这段文字，[编排工具文档](../../docs/orchestration-v2/orchestrator-mcp-server.md) 仍沿用 #24560 的说法。

结果是 Agent 只在这句禁令里见到 `t3_thread_send`，`delegate_task` 的工具描述也不提怎样延续子线程，所以多轮修改和复核时每一轮都会新开子代理。新子代理需要重新交接背景，原子代理的对话、证据和对工作区的了解都用不上。

上游 eval 把「第 2 轮审查发给原审阅者」记为错误，依据是维护者偏好每轮都做独立审查。本 Fork 改为由 Agent 每轮自行判断：延续原子线程能保留上下文、降低交接成本；新开能摆脱前几轮结论的影响。提示词写明两种做法各自的判断依据，不规定只用其中一种。

延续时还要选对子线程。第一版规则写作「下一步建立在某个子代理的工作、证据或发现之上时延续它」，在安装包实测中，Agent 两次把按审查意见修改代码的工作发给了审阅者，并让它从只读审查转为修改。修改依据确实来自审阅者，但这样一来，审阅者要复核的是自己的改动，复核不再独立；写代码的子代理也没能用上它对代码的了解。因此规则按子代理的职责分派后续工作，并要求审阅者保持只审查。

## 行为约定

- 准备再次调用 `delegate_task` 前，先查看已有的子代理，包括已完成的，每一轮都在延续和新开之间做选择。派发时设置 `role`，后续轮次据此区分哪个子代理负责实现、调查或审查。
- 延续时，选择下一步所依托的产出属于哪个子代理，就发给哪个子代理，用 `t3_thread_send` 发到它的 `childThreadId`，并说明自上一轮以来的变化和要回报的内容：
  - 修改代码，包括按审查意见修改，交给写这段代码的子代理；
  - 复核问题是否修好，交给提出这些问题的审阅者；
  - 继续深入调查，交给做这项调查的子代理。
- 审阅者只审查：除非用户要求，不把它审查的代码交给它修改，否则它无法再独立复核。代码由父代理自己写时，父代理自己修改或新开实现者。
- 以下情况新开 `delegate_task`，交接原始任务、已有发现和尚有争议的意见：这一轮需要不受前几轮影响的视角，例如首次审查（不交给写代码的子代理）、终审或用户要求全新视角、审阅者已经认可后再审一轮；需要换模型或设置；原子代理的上下文已过时，或者装不下下一步。
- 已完成的子线程收到消息后会开始新任务，并返回新的 `taskId`。
- 小的审查问题仍由父代理自己修改；被要求不用委派或减少委派时，仍用 `task_cancel` 取消多出的任务。
- 不改变工具注册、任务追踪和取消语义。对原任务调用 `task_cancel` 时，它在子线程中的后续运行仍会一并停止。

## 修改方式

- **共享提示词**：把 [orchestrationInstructions.ts](../../packages/provider-core/src/server/orchestrationInstructions.ts) 中的禁令条目改写为上述判断规则，拆成选择、按职责延续、审阅者只审查、新开四条，「小问题自己修」和取消多余委派两句原文单独保留为一条。
- **工具描述**：在 [delegate_task](../../apps/server/src/mcp/toolkits/orchestrator/tools.ts) 描述中关于 `taskId` 用途的那句之后，补充延续子线程的方式，让 Agent 选择工具时也能看到。`t3_thread_send` 的描述已经说明发往已完成子线程会开始新任务，保持上游原样。
- **测试与预算**：[Codex 上下文测试](../../apps/server/src/provider/CodexDeveloperInstructions.test.ts) 的断言改为检查新规则；[agentContextBudget.json](../../apps/server/src/provider/agentContextBudget.json) 中的提示词和工具列表字节快照随本补丁更新。
- **Eval**：
  - 把 [orchestration.ndjson](../../evals/mcp-tool-use/cases/orchestration.ndjson) 中 `review-round-uses-thread-send` 和 `review-followup-ask-sol-to-confirm` 的期望反转：改为向原审阅者的子线程发送消息，并携带上一轮的发现。
  - 新增 [fork-child-reuse.ndjson](../../evals/mcp-tool-use/cases/fork-child-reuse.ndjson)：
    - `implementer-fix-continues-child`（bad）要求原实现者处理已采纳的审查意见；
    - `review-fix-not-sent-to-reviewer`（bad）的用户请求以审阅者的验证结果为依据，仍要求把修改发给原实现者，不发给审阅者；
    - `final-pass-fresh-reviewer`（guard）要求在需要全新视角时新开审阅者。
- 编排工具文档本来就写着独立审查新开、后续工作延续子线程，不需要修改。

## 验证方式

源码层面运行 Codex 上下文测试、[共享指令测试](../../packages/provider-core/src/server/orchestrationInstructions.test.ts)、[上下文预算测试](../../apps/server/src/provider/AgentContextBudget.test.ts) 和 [eval grader 测试](../../evals/mcp-tool-use/run.test.ts)，并用 `--dry-run` 确认上述五个用例都能构建。

模型行为用 [mcp-tool-use](../../evals/mcp-tool-use/README.md) eval 检查：

- 上述五个用例中，`final-pass-fresh-reviewer` 在上游文字上也应通过，其余四个在上游文字上应失败；五个用例在本补丁的文字上都应通过；
- 同时运行 `orchestration` 区域的其余用例，确认没有回退，重点看 `stale-review-not-cancelled-on-ship`、`review-round-per-bot-nit` 和 `too-many-delegates-cancel-extras`。

最后在安装包中实际跑「实现 → 审查 → 修改 → 复核 → 终审」，确认：

- 修改发给原实现者，复核发给原审阅者；
- 用户的修改请求以审阅者的发现为依据时，修改仍发给原实现者；
- 要求全新视角时新开审阅者；
- 小问题由父代理自己修改。

## 移除条件

满足以下条件后，不再迁移本补丁：上游提示词恢复为由 Agent 在延续子线程和新开委派之间自行判断，并在 `delegate_task` 描述或共享提示词中说明延续方式，且经 eval 和实际派发验证。
